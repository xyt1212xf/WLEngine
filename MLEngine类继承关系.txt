=== 设计纪律 (UE Conformance Rules, 2026-10-13 定) ===
--------------------------------------------------------------------------------
原则: 功能可精简, 设计不对齐 UE 就是债。下面这些规则是新代码必须遵守的。

R1. 渲染线程不分配: _Flush / Render 路径上不允许 new / delete。
    UE 对标: FMeshPassProcessor::BuildMeshDrawCommands 预生成, FMeshDrawCommand
    一次性提交, render thread 只 set state + draw。

R2. 渲染线程不查 shader 名: FMeshBatch 只携带指针, 不携带 shader name。
    UE 对标: FMeshBatch::MaterialRenderProxy*, 名字查询在 Material::CacheShaders
    阶段就完成, render thread 不再解析字符串。

R3. Material 不感知 InputLayout: PSO 的 layout 来自 VertexFactory。
    UE 对标: FMaterial 不持有 vertex declaration; FGraphicsPipelineStateInitializer
    拼装阶段才合并 VF::GetVertexDeclaration() + Material::GetShader()。
    → CMaterial::InitRHI(CStaticVertexFactory*, DepthFormat) 是唯一合法签名,
      禁止再传 TArray<D3D12_INPUT_ELEMENT_DESC>。

R4. Material 不感知 RenderTarget/DepthStencil: depth format 是 render pass 的事。
    UE 对标: FRHIRenderPassInfo 持有深度格式, FMaterial 不参与。
    P0 简化: InitRHI 接收 DepthFormat 作 PSO 创建参数, 但 material 不保存它。
    P1 升级: DepthFormat 完全移到 renderer / render pass 拼装。

R5. DefaultMaterial 生命周期由 CGraphicPlug 拥有, 不由 MaterialMgr。
    UE 对标: GEngine->DefaultMaterial 由 engine 启动期建、关闭期删;
    MaterialResourceMap 只持 weak ref。
    → GraphicPlug::UnInitialise 必须先 delete DefaultMaterial 再 delete device,
      否则 PSO 内的 ID3D12PipelineState 引用悬空 (debug layer 会爆 warning)。

R6. 子系统通过 CMgr 抽象, CEngine 统一驱动 Init/Shutdown。
    UE 对标: IModuleInterface / IEngineModule。
    → 新增子系统必须 : CMgr, 然后在 CEngine::Initialise 加入 mMgrs。

R7. 全局访问走 GEngine->GetXxxMgr()。
    UE 对标: GEngine->XxxManager。
    → 禁止再出现 Mgr::StaticMethod() 形式的调用, 一律走 mgr 实例。

R8. 资源释放顺序: 先释放依赖方, 再释放被依赖方。
    UE 对标: 析构顺序 = 创建顺序反向 + 引用图反向。
    → 典型链路: Renderer → Material(PSO) → Device(ID3D12*)。

R9. DX12 API 只允许出现在 DX12*.h/.cpp 中 (既有纪律, 继续)。
R10. 公开类加 MLENGINE_API 导出标记 (既有纪律, 继续)。

R11. P0 简化必须明确标注 "P1/P2 升级到 XXX", 写在本文件"问题"区,
    不允许悄悄"以后再说"。本次审计列出 8 项, 详见下文。

四、三条主要数据流
--------------------------------------------------------------------------------

◆ 流程 A: 静态网格数据管线 (CPU + GPU 侧均通)
  CreateCube() 填拓扑
    → FMeshDescription (Vertex/VertexInstance/Triangle/PolygonGroup)
    → CMeshAttributes::BakeFromDescription()   平铺 + 按材质分组
    → CStaticMeshLODResources::InitResources() 创建 4 个 VB/IB 并上传 GPU
    → VertexFactory Schema 填好, BuildInputLayout 缓存 VB 视图

◆ 流程 B: 世界加载管线 (状态机已通, Lua 关卡文件驱动)
  CEngine::LoadScene → CWorld::LoadAsync (线程池 threadDetach)
    → LoadPersistentLevel()   (UE UWorld: 只负责持有 map 包里的 ULevel)
       ├─ 创建 CLevel, 以 level 名给 World 命名
       └─ CLevel::Load(FilePath, &StreamingDescs)   ★UE ULevel::Serialize
            独立沙箱 lua_State (base/table/math/string) dofile 关卡文件
            → Name / Actors[] (CActor + CStaticMeshComponent + CStaticMesh)
            → StreamingLevels[] 回传给 CWorld (那是 UWorld 的数据)
            读完即 lua_close, 不接触 CScriptPlug 的游戏逻辑 VM
    → 登记 StreamingLevels → 状态 UploadingGPU
    → 主线程 TickLoad: UploadGPUResources() [空] + InitActorsForPlay() → Ready
    → CWorld::Tick: 主关卡 Actor::Tick + 组件 tick; 流送关卡 Actor::Tick
  关卡文件格式: Run/Resource/Level/DefaultLevel.me (Lua table 字面量)

◆ 流程 C: 渲染帧循环 (★本版重写, 走 UE 材质驱动的数据流)
  初始化阶段 (主线程, CEngine::Initialise + GraphicPlug::Initialise):
    CEngine::Initialise:
      1. mpShaderMgr = new CShaderMgr();   Init() → CGlobalShaderMap::InitGlobalShaders
      2. mpMaterialMgr = new CMaterialMgr(); Init() → P0 no-op
    GraphicPlug::Initialise (in same call, after mgrs):
      3. new CMaterial → SetShaders("CSolidColorVS","CSolidColorPS")
      4. DefaultMaterial->InitRHI(FallbackLayout, D32)   // 从 GEngine->GetShaderMgr() 查 shader
      5. GEngine->GetMaterialMgr()->Register("Default", ...) + SetDefaultMaterial(...)

  帧循环 (渲染线程, CRenderer::_Draw):
    _Begin  → CDX12RHIDevice::BeginDraw
    _Flush  → 计算 View/Proj
              → pWorld->CollectVisibleMeshes(View, OutBatches)
                (遍历 Actor→CStaticMeshComponent::GetMeshBatch
                 → OutBatch.Material = Mesh->GetMaterialForSection(SectionIndex)
                   其中 GetMaterialForSection 走 GEngine->GetMaterialMgr()->GetDefaultMaterial)
              → 遍历 Batches:
                 PSO = Batch.Material->GetPipelineState()
                 (PSO 变化时才切 SetPipelineState + SetGraphicsRootSignature)
                 SetGraphicsRoot32BitConstants(0, 16, MVP)   // World*View*Proj
                 IASetVertexBuffers / IASetIndexBuffer
                 DrawIndexedInstanced
    _End    → CDX12RHIDevice::EndDraw

  关引擎 (CEngine::UnInitialise):
    1. 删 World
    2. 删 Plugs (graphic plug → device + default material)
    3. 反向遍历 mMgrs: Shutdown + delete (materialMgr 先, shaderMgr 后)

  注: _Flush 内不再出现 new / CSolidColorVS / CPipelineState / GetShader<>,
      全部数据由 FMeshBatch.Material 提供 (UE 同款 FMeshPassProcessor 思路简化版)。

六、当前设计问题（按严重度排序）
--------------------------------------------------------------------------------
【已解决·原问题2】Transform 已上移到 CSceneComponent，子类残留字段已删除，
                   组件析构泄漏也已修复。

【已解决·原问题3】CActor 构造时即 AddComponent<CSceneComponent>() 作为 RootComponent。
                   残留语义缺口: 尚无任意层级的 AttachToComponent (P2 解决)。
                   ★P1-P 进展(2026-10-16): CSceneComponent 已支持 AttachParent +
                   GetWorldMatrix 逐级乘父级; AddComponent 会把非 root 的 scene
                   组件自动挂到 RootComponent, 因此 AActor::SetActorTransform
                   (只写 root) 现已能传导到 mesh 组件 —— 修复了"关卡里改 Actor
                   位置无效、cube 恒在原点"的 bug。
                   仍缺: 挂到非 root 父级 / DetachFromComponent / RemoveComponent /
                   环检测(GetWorldMatrix 递归会栈溢出)。

【问题1】CRHIBuffer 继承方向反了 (结构性, ★用户已决定不改, 仅存档)
  现状: CRHIBuffer : CDX12RHIBuffer  (抽象层继承实现层)
  UE 的做法: FRHIBuffer 是纯虚基类, FD3D12Buffer : FRHIBuffer 是实现。
  结论: mini 引擎只做 DX12, 保持现状可接受。

【架构决策·图形API层统一约定 (2026-10-11 定)】
  所有图形API相关类统一采用 "C抽象类 : CDX12具体类" 方向:
    CShader : CDX12Shader : CResource, CRHIBuffer : CDX12RHIBuffer
    CPipelineState : CDX12PipelineState (新增, 同模式)
  将来换 API 用宏在编译期切换基类 (如切到 COpenGLShader)。
  (UE 是"抽象基类 + 实现子类", 方向相反; 用户明确选择不改)
  配套纪律(保证宏切换可行):
    1. 具体 API 类(CDX12*)不暴露给上层 —— DX12 专属类型/头文件
       (ID3DBlob/D3D12_*/d3d12.h) 只允许出现在 DX12*.h/.cpp 中
    2. GlobalShader/Renderer/SolidColorShader/Material 等上层文件禁止出现任何
       ID3D*/D3D12_* 类型
    3. DX12 类的创建集中在一处(宏/工厂), 不许上层直接 new CDX12*

  ★本版新增: CRenderer.cpp 已通过 linter 检查, 全文不出现 ID3D*/D3D12_* 之外的
    渲染API 直接引用 (只通过 CPipelineState 接口访问 ID3D12RootSignature /
    ID3D12PipelineState)。这意味着将来切到 Vulkan/Vulkan_RHI 只需替换 DX12 类
    实现, renderer 一行不用改。

【问题4】CWorld 的所有权与线程安全 (正确性, 未变)
  - CLevel::Load 里 new 的 CStaticMesh/CActor 无处释放(CActor/CLevel 析构为空)。
  - LoadAsync 后台线程 CLevel::Load 与主线程 TickLoad/Tick 无同步。
  - 渲染线程 _Flush 读 World/FMeshBatch, 与游戏线程 Tick 并发无同步。
  - 建议: 最低限度在 LoadState 上加原子量/临界区; 析构补齐释放; 渲染数据双缓冲。

【问题5→已部分解决】GetMeshBatch 硬编码 LOD0/Section0
  旧: 完全硬编码, 不查 Section.MaterialIndex。
  现: Section 仍固定 0, 但已经从 Section[0].MaterialIndex 查到了 CMaterial* 填到 batch。
       LOD 切换仍是 P2; 同一 LOD 内的多 section 遍历也是 P2。
  (Multi-section / multi-material cube 出屏时再补, 不影响当前 P0 调试。)

【问题6→架构层面已松绑】FMeshBatch 耦合 CStaticMesh
  旧: FMeshBatch 字段里 CStaticMesh* 是 renderer 不需要的数据。
  现: FMeshBatch 仍然存 CStaticMesh* (CStaticMeshLODResources 也是
       forward-decl), 但 renderer._Flush 不再访问它 (只用 LOD/VertexFactory/
       Material/WorldMatrix/Element)。在 UE 里 FMeshBatch 不认 UStaticMesh 也
       是因为 mesh 的元数据已经迁到 FPrimitiveSceneProxy; mini 阶段保留指针
       是为了 component 端回写, 不影响渲染路径。

【问题7】CMaterial 当前未受 CRefcount 保护 (P1 后续)
